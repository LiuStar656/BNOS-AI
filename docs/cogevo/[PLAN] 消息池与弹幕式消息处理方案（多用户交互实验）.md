## 一、实验场景与目标

### 1.1 实验定位

本方案是**实验设计方案**：搭建一个多 Agent 仿真平台，平台维护一个聊天室式的消息池，多个标准 BNOS AI（AAA 认知节点）订阅消息池、处理消息、按需发言。验证两件事：

1. **多用户交互能力**：AAA 能否在消息池中区分不同用户（不同 user_id），对每个用户建立独立的认知并选择性回应。
2. **多用户场景下的认知演化**：在高并发、多数忽略、少数回应的消息流中，AAA 的自我认知、他人认知、情感、性格是否持续演化，数据是否可采集、可分析。

### 1.2 平台与 Agent 的边界

| 职责 | 归属 |
|------|------|
| 消息池（订阅/批量派发/去重/洪流控制） | 平台 |
| 发言仲裁（同一时刻一条发言） | 平台 |
| @ 点名路由（谁被点名谁先回） | 平台 |
| 接收消息、处理消息、输出消息 | Agent（AAA 节点，黑盒） |
| 想不想说话、说什么 | Agent（LLM 决策） |

对每个 Agent 而言，其他 Agent 只是"其他用户"——它们发出的消息带 user_id 进入消息池，与真实用户无异。Agent 自身**不感知**平台的存在。

### 1.3 核心实验原则

**接收消息后处理消息，不一定要发言。** 消息池像聊天室：绝大多数消息被"听到"，只有少数被"回应"。处理（认知更新、想法记录）与发言（对外广播）是两个独立阶段，必须解耦。

## 三、需要补齐的功能（针对实验场景）

### F1 消息池订阅接口

**实验需求**：聊天室式消息以高并发、批量方式到达，Agent 需要订阅消息池并按批消费，不能逐条触发 LLM。

**现状**：`_on_text(data, dbp)` 每次调用处理一条文本，直接构建 prompt。无批量入口、无订阅语义。

**补齐设计**：

1. 平台侧维护消息池队列（对齐 Lumi_Nox `SpeakerScheduler`）：
   - `enqueue_input(text, source, uid, ...)`：消息入队，**不打断** Agent 当前处理。
   - `pop_all_inputs(max_items)`：批量取出，同人同文去重，洪流按"付费 > 最新消息 > 互动"配额取舍。
2. AAA 侧新增批量入口 `_on_pool_batch(messages, dbp)`：
   - 接收平台打包的一批消息（每条带 `speaker_id` / `user_id`）。
   - 与 `_on_text` 并存：GUI 直连仍走单条路径，消息池走批量路径。

**落点**：`main.py` 新增 handler；平台侧新增消息池组件。

### F2 user_id 维度

**实验需求**：验证"用户信息表里出现不同 id 的用户信息"——记忆数据必须能归属到具体用户，实验才能证明多用户认知发生。

**现状**：`user_messages`、`feelings`、`event_summary`、`self_cognition`、`other_cognition`、`user_facts`、`self_info` 全部只有 `identity_key`（AI 自己）与 `conversation_id`，**没有谁在说话的字段**。`db._write` 与 `db._write_parsed` 写入时不区分消息来源用户。

**补齐设计**（v3 幂等迁移，沿用现有 `ALTER TABLE ADD COLUMN` 模式）：

| 表 | 新增列 | 语义 |
|----|--------|------|
| `user_messages` | `user_id TEXT DEFAULT ''` | 这条消息是谁发的（空 = AI 自己或匿名） |
| `feelings` | 不迁移（想法归属 AI 自身） | — |
| `event_summary` | `user_id TEXT DEFAULT ''` | 该事件由哪个用户触发 |
| `other_cognition` | `user_id TEXT DEFAULT ''` | 对"哪个用户"的新认识 |
| `user_facts` | `user_id TEXT DEFAULT ''` | 关于"哪个用户"的事实 |

写入侧：`_write` / `_write_parsed` 增加 `user_id` 参数，从输入数据 `data.get("user_id")` 取值，缺省 `""`。

**落点**：`db.py` `ensure()` 迁移段 + `_write` / `_write_parsed`。

### F3 多用户认知存储与检索

**实验需求**：对用户 A 的认知不能混入对用户 B 的认知；与 A 对话时只注入 A 的记忆。实验要通过"检索是否精确区分用户"来验证多用户认知能力。

**现状**：`_gather_context` 按 `identity_key + conversation_id` 检索 `other_cognition` / `user_facts` / `feelings`，无用户维度过滤。多用户同会话（聊天室场景默认同会话）时，A 和 B 的认知会混在一起。

**补齐设计**：

1. 检索过滤：`_gather_context` 增加 `user_id` 参数。`other_cognition` / `user_facts` 检索加 `WHERE user_id = ?`（`user_id = ''` 的全局认知兜底保留）。
2. 提示词注入：`prompt.py` 的"他人认知"段按当前说话用户注入，格式：
   ```
   你的他人认知（对 用户A）：...
   ```
3. 会话内多用户：聊天室场景所有用户共享 `conversation_id`，靠 `user_id` 列区分归属，不再依赖 `conversation_id` 切分。

**落点**：`db.py` 查询函数、`main.py` `_gather_context`、`prompt.py`。

### F4 静默处理通道

**实验需求**：接收消息后处理消息不一定要发言——Agent 听到一条消息，更新了想法和认知，但选择不说话。这是本方案的核心机制。

**现状**：输出侧已具备基础：`_on_parsed` 中 `if parsed.get("自然回复")` 为空则不产出发言输出，`想法` / `心情` 仍入库。但平台侧无法区分"Agent 处理完选择了沉默"与"Agent 没响应"。

**补齐设计**：

1. `_on_parsed` 返回结构增加显式结果类型：
   ```json
   {"action": "reply" | "silent", "content": "..."}
   ```
   - `reply`：自然回复非空，走平台广播。
   - `silent`：自然回复为空，只写记忆，平台记录"已处理、未发言"。
2. 平台侧对 `silent` 结果标记该消息"已消费"，避免重复派发；同时记录静默决策供实验分析（见 F8）。
3. 静默时认知演化照常：`_process_mood_and_evolution` 与后台反思不因未发言而跳过。

**落点**：`main.py` `_on_parsed` 返回值扩展；平台消息池消费协议。

### F5 批量输入合并上下文

**实验需求**：一批聊天室消息（含多个用户、多条消息）只触发一次 LLM 调用，且模型能感知"谁说了什么"。

**现状**：`_gather_context` 只接受单条 `user_text`。

**补齐设计**：

1. `_gather_context` 支持 `batch_items` 参数，注入格式（对齐 Lumi 合并消息的实践）：
   ```
   本轮消息池消息（按时间正序）：
   [用户A] 消息1
   [用户B] 消息2
   [用户A] 消息3
   ```
2. 批量输入时 `user_text` 用合并文本，`user_id` 取"最后发言的用户"（决定检索注入对象），其余用户作为旁观语境。
3. `想法` 与 `自然回复` 均基于批量上下文生成；回复默认面向最后发言用户。

**落点**：`main.py` `_gather_context`、`prompt.py` 上下文头。

### F6 发言仲裁与路由

**实验需求**：同一时刻只允许一个 Agent 对外发言；聊天室消息 @ 了某 Agent 时优先路由给它，防止多个 Agent 抢答同一条消息。

**现状**：平台无仲裁器、无路由。多 Agent 各自独立处理消息池，可能同时回复。

**补齐设计**（对齐 Lumi_Nox `SpeechOutputArbiter` + `SpeakerScheduler`）：

1. 仲裁器：全局单例，同一时刻一个 Agent 持有"发言权"。
   - `POLICY_QUEUE`：当前有人发言则排队（默认）。
   - `POLICY_DROP`：发言中则丢弃本次输出（Agent 已处理、不发言，等于静默）。
   - `POLICY_INTERRUPT`：高优先级消息（如 @ 点名）打断当前发言。
2. 路由：消息入池时检测 @ 点名（对齐 Lumi `pick_speaker`）：
   - @ 了单个 Agent → 该 Agent 优先处理该批消息。
   - 无 @ → 按轮换或全部 Agent 独立评估（各自决定要不要回应，由仲裁器收敛最终发言者）。
3. 仲裁器事件发布到 EventBus：`speech_output_started / queued / dropped / cancelled`，供实验数据采集。

**落点**：平台侧新增 `arbiter.py` / `router.py`（参考 Lumi 实现）。

### F7 后台监听认知更新

**实验需求**：其他 AI 说话时，Agent 在后台"自己听、自己思考、自己更新状态"，不打断当前处理。

**现状**：`_trigger_background_review` 每 5 轮触发一次自我反思，但依赖对话轮计数；静默观察的消息不进入认知演化管线。

**补齐设计**：

1. 静默处理（F4）走完整的认知演化路径：`_process_mood_and_evolution` + 事件摘要写入 + `_trigger_background_review` 计数。
2. 监听计数独立于发言计数：`_observe_counter` 每消费一批消息 +1，每 N 批触发一次后台反思（对齐现有"每 5 轮"节奏）。
3. 后台反思线程读取的消息包含 `user_id`（F2），反思结果 `other_cognition` 带用户维度（F3）。

**落点**：`main.py` 静默路径 + 反思触发逻辑。

### F8 实验数据采集

**实验需求**：实验结束后能回答"多用户认知是否发生、认知如何演化"——需要结构化数据。

**现状**：无实验专用数据输出。

**补齐设计**：

1. 平台侧事件日志（EventBus 订阅）：每条消息入池/派发/被处理/被回复/被仲裁丢弃，记录时间戳、user_id、目标 Agent。
2. Agent 侧决策日志：每批消息的响应 `{action: reply|silent, user_id, 想法, 回复摘要, 性格向量快照, 心情}`。
3. 输出格式：JSON Lines，按实验轮次落盘，与认知演化实验报告对接（`runs/` 目录约定）。

**落点**：平台事件采集器 + Agent 决策钩子。

## 四、补齐后的完整数据流

```
[Agent A] [Agent B] ... [Agent N]          平台
    │          │             │
    ▼          ▼             ▼
┌─────────────────────────────────────────────┐
│ 消息池（enqueue_input，不打断，去重+洪流）   │
│ → 批量打包 pop_all_inputs(max_items)        │
│ → 路由 router：@点名 / 轮换                  │
│ → 派发 _on_pool_batch(messages)             │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ AAA 节点（黑盒）                             │
│ 1. _gather_context：user_id 过滤检索 + 合并  │
│    批量上下文                                │
│ 2. LLM：想法 + 自然回复（可空）              │
│ 3. 认知演化：风格观测 → 性格/心情/他人认知   │
│ 4. 后台反思：静默也计数，定期沉淀自我认知    │
│ 5. 输出：{action: reply|silent, ...}        │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│ 仲裁器 SpeechOutputArbiter                  │
│ reply → 广播（唯一发言权）                  │
│ silent → 静默（只写记忆，标记已消费）        │
└─────────────────────────────────────────────┘
    │
    ▼
实验数据采集（平台事件日志 + Agent 决策日志）
```

## 六、实验验证与数据收集

### 6.1 多用户认知能力验证

| 验证点 | 判定标准 |
|--------|---------|
| 用户区分 | `user_facts` / `other_cognition` 中出现不同 user_id 的独立条目 |
| 认知隔离 | 与用户 A 对话时，注入的记忆不包含用户 B 的事实（检查 prompt 日志） |
| 选择性回应 | 消息池中大部分消息 `action=silent`，少数 `action=reply`，回复目标用户正确 |
| 发言唯一性 | 同一批消息最多一个 Agent 实际发言（仲裁器日志无并发发言） |
| 静默也演化 | 静默轮次中 `feelings.thought` / `event_summary` 仍有写入 |

### 6.2 认知演化数据收集

沿用认知演化实验的 `runs/` 目录约定，每次实验输出：

- `events.jsonl`：平台消息池事件（入池、派发、仲裁、广播）。
- `decisions.jsonl`：Agent 每批消息的响应决策（reply/silent、user_id、想法、性格向量快照）。
- `evolution.json`：实验起止的性格向量、情感趋势、他人认知条目数（按 user_id 分组）。

分析维度：多用户场景下性格向量是否仍收敛（对照 E2 中心收敛结论）、不同用户是否触发不同认知分支、静默比例与回复比例的演化曲线。

## 七、验收方法

### 7.1 功能验收

1. 模拟 3 个用户 + 2 个 Agent，消息池连续注入 100 条消息（含重复、@ 点名、无点名），观察：
   - LLM 调用次数 ≈ 批次数（而非消息数）。
   - @ 点名消息由被点名 Agent 优先处理。
   - 同一时刻至多一个 Agent 发言。
2. 查询数据库：`user_messages` / `user_facts` / `other_cognition` 均含正确的 `user_id` 归属。
3. 静默场景：Agent 只更新想法与认知，不产生对外广播，消息池标记该消息已消费。

### 7.2 实验数据验收

1. `events.jsonl` / `decisions.jsonl` 完整覆盖实验全程，字段无缺失。
2. `evolution.json` 中性格向量、情感、他人认知按 user_id 分组可统计。
3. 数据可直接对接认知演化实验分析流程（P0 实验报告格式）。
