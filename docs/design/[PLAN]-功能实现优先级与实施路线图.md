## 一、评估标准

采用**三维加权评分法**，综合评估每个方案的"见效速度"：

| 维度 | 权重 | 说明 |
|------|:----:|------|
| **用户可感知度** | 40% | 0-5分，用户能直接感受到的变化程度 |
| **开发工作量** | 35% | 完成全部功能所需的工作日数 |
| **技术难度系数** | 25% | 0-5分，代码复杂度/调试难度/技术风险 |

### 综合评分公式

```
性价比 = 用户可感知度 ÷ (工作量 × 难度系数)
```

**解读**：
- 性价比越高 = 越值得优先实施
- 高感知度 + 低工作量 + 低难度 = 立即优先
- 低感知度 + 高工作量 + 高难度 = 暂缓实施

### 评分标准明细

#### 用户可感知度（0-5分）

| 分值 | 标准 | 示例 |
|:----:|------|------|
| 5 | 从部署第一分钟起，用户就能看到/感受到显著变化 | AI性格变化、3D角色换装 |
| 4 | 短期使用后可明显感知，有"惊喜感" | AI记忆提升、主动搭话 |
| 3 | 持续使用后可感知，改善体验 | GUI视觉优化、情绪曲线 |
| 2 | 需要专业用户才能感知，或改善有限 | CLI工具、插件系统 |
| 1 | 用户完全不感知，仅为开发者便利 | AAA底层改造 |

#### 技术难度系数（0-5分）

| 分值 | 标准 | 示例 |
|:----:|------|------|
| 1 | 纯配置改动或简单SQL/JSON | 加字段、改模板 |
| 2 | 标准Python实现，无第三方依赖 | 状态机、文件扫描 |
| 3 | 需要第三方库或复杂逻辑 | QPainter、Curses、SQLite查询优化 |
| 4 | 涉及实时流或多线程 | 音频流处理、WebSocket |
| 5 | 涉及新技术栈或高调试难度 | Three.js/VRM、MToon Shader |

### 2.2 Top 3 深度分析

#### 🥇 AI世界感知记忆系统（性价比 11.43）

**方案文档**：[PLAN]-AI世界感知记忆系统设计方案.md

**为什么排第一？**

| 评估项 | 详情 |
|--------|------|
| **开发周期** | 半天完成（0.35天） |
| **改动范围** | 仅改动 `db.py` + `memos.py`，加 2 个字段和 1 个查询条件 |
| **技术难度** | ⭐ 最低，纯 SQLite 字段扩展 + 写入逻辑 |
| **用户感知** | ⭐⭐⭐⭐ 高，AI 记忆质量立刻提升 |
| **风险等级** | 零风险，最坏情况是记忆质量没提升，绝不会变差 |

**核心改动**：

```python
# 1. db.py: 加字段
ALTER TABLE long_term_memory ADD COLUMN entity TEXT DEFAULT NULL;
ALTER TABLE long_term_memory ADD COLUMN channel TEXT DEFAULT 'chat';

# 2. 写入逻辑: 同实体覆盖
if entity:
    old = db.execute("SELECT id FROM long_term_memory WHERE entity=? AND status='active'")
    if old:
        db.execute("UPDATE long_term_memory SET status='superseded' WHERE id=?", (old[0],))

# 3. 检索逻辑: 状态过滤
results = memos.retrieve(query)
return [r for r in results if r.get("status") == "active"]
```

**效果对比**：

| 场景 | 改造前 | 改造后 |
|------|--------|--------|
| 用户提到"我的红杯子" | AI 可能回忆起"杯子"的多条记录（含过期信息） | AI 准确回忆起"红杯子在玄关，上次你说它漏水" |
| 物品位置变化 | AI 可能混淆新旧位置 | AI 只返回最新的位置信息 |
| 记忆冲突 | 多条记录并存，AI 可能输出矛盾信息 | 旧记录自动标记 `superseded`，只返回最新 |

**代码量**：约 30 行 Python + 2 条 SQL

**依赖**：无任何依赖，不需要新库、不需要新节点、不需要硬件

| 方案间数据模型冲突 | 中 | 低 | 统一 `identity_key` 和 `data_type` 命名规范 |
| 依赖方案未就绪 | 高 | 中 | Phase 实施时标注"前置条件"，未就绪时跳过 |
| 技术方案不可行 | 高 | 低 | 每个 Phase 开始前做技术预验证（0.5天） |
| 代码量超出预估 | 中 | 中 | 每个方案预留 20% 缓冲时间 |
| 用户反馈不符合预期 | 中 | 低 | 每个 Phase 结束后做用户体验测试 |

### 6.2 快速迭代策略

```
周例会：
  - 每周末评估本周交付物
  - 用户测试 + 反馈收集
  - 动态调整下周优先级

迭代原则：
  - 交付即测试
  - 测试即反馈
  - 反馈即迭代
```
