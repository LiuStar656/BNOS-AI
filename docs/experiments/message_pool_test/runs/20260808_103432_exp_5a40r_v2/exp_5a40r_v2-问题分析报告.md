## 三、本次暴露的问题

### 问题 1：API 失败被静默吞掉，静默统计被污染（严重）

189 条 `HTTP 402` 失败记录全部写入 decisions.jsonl 且 `action="silent"`、想法/心情为空、带 error 字段。后果：

- evolution.json 的 silent_count（197 条）中 **96% 是假静默**，静默率 84% 是虚假指标；
- 真实静默率应为 17.8%（8/45），比上一轮 32% 还低；
- 失败与"主动选择沉默"在数据上无法区分（只能靠 error 字段人工排除）。

**修复方向**：失败调用应记录为独立 action（如 `error`）或带 error 标记过滤，绝不能落入 silent 分支；silent 统计必须排除 error 记录。

### 问题 2：静默记录 user_id 归因 bug 复现（批次末尾偏置，严重）

所有 8 条正常静默 + 189 条失败记录，`user_id` 一律等于**该批次最后一条消息的发送者**（而非实际处理对象）：

| 记录 | 批次内容 | 记录 user_id | 实际末尾发送者 |
|---|---|---|---|
| round_2_agent_3 (silent) | [agent:0,1,2,3,4] | agent:4 | agent:4（错） |
| round_4_agent_0/1 (silent) | [agent:0,1,3,4] | agent:4 | agent:4（错） |
| round_7_agent_1/2 (silent) | [agent:0,1,2,3] | agent:3 | agent:3（错） |
| round_13 全部 | [userD,userA,userC,userF,userB,userB] | userB | userB（错） |
| round_15 全部 | [userA,userD,userA,userD] | userD | userD（错） |

该 bug 在 n3_25r 已出现（4 条静默全指 agent:2），本轮再次复现，说明静默分支的 user_id 填充逻辑从未修复：**它取 batch_context 最后一项的 user_id，而不是模型实际回应的对象**。静默时"回应对象"字段为空，采集层就用批次末尾兜底。

### 问题 3：认知矩阵出现双黑洞——agent:0 与 agent:1 被全员忽略（机制性问题）

互认矩阵中，**没有任何 agent 形成对 agent:0 和 agent:1 的认知**（两列全 0），尽管 agent:0 发言 9 条、agent:1 发言 8 条，是活跃参与者。相互认知只在 agent:2/3/4 三角内形成（2↔3、2↔4、3↔4 双向）。

根因：认知只针对"直接回复对象"，而**回应对象选择存在强烈的末位偏置**——模型几乎总是回复批次里最后一条消息的发送者：

- round_3（批次 [agent:0,1,2]）：4 个 agent 全部回复末位的 agent:2；
- round_6（批次 [agent:0,1,2,4]）：4 个 agent 全部回复末位的 agent:4；
- round_4（批次 [agent:0,1,3,4]）：回复者全部回复末位的 agent:4。

agent:0/agent:1 发言总是排在批次前端，从不在末尾，于是永远不被选为回应对象 → 不被认知 → 认知演化对它们完全失效。上一轮黑洞是 agent:1，本轮扩大为 agent:0+agent:1 双黑洞。

**修复方向**：回应对象选择需明确"本轮我要回应谁"的判定（结合 @提及、话题相关性、随机化），消除批次顺序/末位偏差；或在采集层验证 user_id 与模型输出的回应对象一致性。

### 问题 4：人格演化管线仍然断裂（3 次实验全部复现）

5 个 agent 人格向量首末完全一致，欧氏距离全部 0.0000。但本轮新增了更有价值的证据：**情绪链路是通的**——agent:1（俏皮型）情绪从 0.05 升至 0.2636，agent:4 升至 0.0941；而 agent:0/agent:2 全程 0.0。情绪能动、人格不动，精确说明断裂点位于"人格向量更新"环节（_adjust_vector 未接入多用户批量路径），而非整个演化机制失效。对比上一轮（agent:2 情绪升最高 0.4399），俏皮型 agent 的情绪敏感性在两个批次中一致复现。

另注意：agent:0 有 9 条 reply 但 mood 恒为 0.0，暗示情绪更新可能只对特定"心情"标签（如"好奇"）生效，需要核查情绪更新逻辑是否与心情标签耦合。

### 问题 5：轮次计数冲突依旧（第 4 次出现）

- _run_meta.json：rounds=60、topic_rounds=40
- evolution.json / decisions.jsonl：rounds=49
- 用户预期差 11 轮，实际正常对话仅 11 轮、失败 38 轮

多个文件各自记录不同的轮次口径，且 402 中断时没有 topic_ended 收尾事件，无法区分"话题结束"与"运行中断"。

### 问题 6：模拟用户消息验证目标未达成

sim 用户消息注入与欠费同时发生（10:38:16），全部 38 轮用户消息批次无人应答，多用户认知（user_id 维度）验证**完全未测到**——除了留下 189 条失败记录和错误的 user_id 归因。此外，sim 语料有明显重复（"最近有什么新闻吗""我好像感冒了""推荐一首歌吧"等被多个 user 复述），虽然去重机制兜住了，但语料多样性不足。

## 五、结论与优先级

**已确认修复**：llm_stats 统计链路、模拟用户注入、消息去重。

**待修复（按优先级）**：
1. **P0 - 失败记录与静默分离**：402/超时等错误不得落入 silent 分支，须独立标记；静默统计排除 error。
2. **P0 - 静默 user_id 归因**：静默记录 user_id 必须来自模型实际处理对象，不能取批次末尾兜底。
3. **P1 - 回应对象选择偏差**：消除末位偏置，否则部分 agent 永远无法被认知（本轮 agent:0/1）。
4. **P1 - 人格演化管线**：将 _adjust_vector 接入多用户批量路径，并核查情绪更新与心情标签的耦合。
5. **P2 - 轮次口径统一**：_run_meta / evolution / decisions / events 使用同一轮次来源。
6. **P2 - sim 语料扩展**：增加模拟用户消息多样性；注入时机避开 API 不稳定期，确保用户消息轮与 agent 轮交织（先验证 agent 对话再混入用户）。
